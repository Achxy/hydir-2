Building HydIR: a narrow path from binaries to LLVM IR—and back

HydIR Project ◆ September 18, 2026 ◆ 12 min read

TL;DR: HydIR is an independently implemented binary-lifting workbench built around a simple rule: when the tool cannot justify a transformation, it stops. Today it imports little-endian x86-64 ELF files, recovers a deliberately small control-flow subset, emits LLVM IR and bounded C, and can rebuild a narrowly defined class of freestanding programs. The useful part is not pretending that this is general decompilation. The useful part is making every supported step inspectable, reproducible, and difficult to overclaim.

The pitch: binary rewriting you can audit

Binary tooling tends to be described from the finish line. A diagram starts with a compiled program and ends with clean source, a patched executable, or a recovered model. The hard middle—instruction semantics, control-flow boundaries, calling conventions, memory, relocations, and proof of behavior—gets compressed into one optimistic arrow.

HydIR starts in that middle. Its first milestone is not “decompile anything.” It is a native vertical slice where each transformation has a small contract and an explicit refusal mode. That makes the early system less spectacular, but much easier to reason about.

A narrow tool that tells the truth is more useful than a broad demo that hides its assumptions.

Why make the first slice so small?

Because a binary lifter has several different jobs, and success in one is not success in all of them. Parsing an ELF proves that the file can be inventoried. Recovering a control-flow graph proves that a bounded set of direct edges can be followed. Emitting LLVM IR proves that the accepted instructions have a translation. None of those alone proves that the translated program behaves like the original.

HydIR keeps those claims separate. The current function-level contract accepts symbol-bounded or analyst-bounded x86-64 code with full-width scalar operations, direct branches, and a declared two-argument SysV ABI. Calls, memory accesses, indirect edges, partial registers, and uninitialized values are rejected on that path. Import is intentionally broader than lift; lift is intentionally broader than rebuild.

One pipeline, five explicit boundaries

1. Import without pretending to understand

The importer records what the file actually says: target and ABI facts, loadable segments, sections, symbols, dynamic imports, and relocations. When a generic parser cannot classify a relocation, HydIR preserves the raw type instead of erasing it. Ordinary inspection marks call and reference recovery as not_attempted; an empty list is never presented as proof that the program has no calls.

hydirctl · local

$ hydirctl inspect ./sample.elf
target       x86_64-unknown-elf
entry        0x401000
calls        not_attempted
references   not_attempted

$ hydirctl cfg ./sample.elf checked_add
status       recovered
edges        direct-only

2. Recover only the control flow in scope

Reachable direct branches must remain inside the selected byte extent and land on valid instruction boundaries. The recovery engine rejects overlapping instructions and edges that escape the declared function. For stripped files, HydIR does not invent symbol discovery; the analyst supplies an entry address and exact size.

3. Lift semantics, not syntax

Accepted instructions become plain LLVM integer operations with explicit flag modeling. Inputs arrive in the expected registers, every returning path must define the return register, and arithmetic keeps wrapping semantics—no convenient nsw or nuw promises are added. The output is intentionally low-level because honest structure is more important than pretty structure.

x86-64

cmp   rdi, rsi
jge   .keep_left
mov   rax, rsi
ret

HydIR → LLVM IR

%cmp = icmp sge i64 %rdi, %rsi
br i1 %cmp, label %keep_left,
             label %take_right

4. Verify artifacts independently

A generated file is not accepted merely because HydIR produced it. The demo pipeline asks LLVM to verify the IR, compiles bounded C independently, and compares both lifted forms with native execution on trusted fixtures. The evidence is differential testing, not a theorem: useful, repeatable, and explicitly limited to the exercised inputs.

5. Rebuild through a separate, stricter contract

Whole-executable rebuilding is not treated as “function lifting, but bigger.” It uses a separate stateful path for freestanding static programs with complete text coverage, direct control flow, bounded mapped data, and a small read/write/exit bridge. Stack accesses, dynamic linking, indirect edges, unknown instructions, and unsupported syscalls are rejected. The rebuilt binary is always written to a new destination.

What the evidence actually says

HydIR’s checked-in evidence records a completed pinned Linux run for the supported subset. These numbers describe fixtures, not arbitrary binaries, and they are kept next to the limitations that make them meaningful.

20 distinct supported scalar functions
21,168 controlled input pairs matched by lifted IR and compiled C
3 freestanding programs rebuilt in the bounded whole-program path
0 claims of general equivalence or hostile-input safety

Reading the numbers: “21,168 matches” means the recorded test cases agreed. It does not mean 21,168 instructions, complete x86-64 support, or a proof that every input agrees.

A workbench around the engine

The engine is exposed through a CLI, an egui desktop application, an authenticated loopback service, and a small Python SDK. The desktop workbench keeps machine bytes, reachable CFG, LLVM IR, bounded C, assumptions, and diagnostics visible at the same time. Local binary opening stays local; upload is a separate labelled action that creates an immutable project revision.

Analyst names, comments, and assumptions live in revisioned ledgers. Assumptions can be overlaid into an analyzed specification, but their provenance remains analyst_assertion. A comment never becomes recovered semantics because it was convenient for the UI.

The refusal list is part of the product

  • No general decompiler. C output covers the same bounded scalar subset and retains explicit CFG structure.
  • No hostile-binary sandbox. Native validation is limited to trusted fixtures; the service exposes no server-side binary execution endpoint.
  • No automatic stripped-code discovery. Entry and extent are analyst inputs when symbols are unavailable.
  • No silent overwrite. Generated artifacts and rebuilt programs go to new paths, or must be byte-identical to an existing output.
  • No import-equals-support shortcut. Knowing that an instruction, relocation, or symbol exists is not the same as having semantics for it.

What comes next?

The next useful work is not a bigger feature list. It is more semantic coverage without weakening the boundary: broader instruction forms, memory and calling behavior, stronger cross-tool differential checks, and better ways to show why a function stopped. Each expansion should arrive with its own fixture corpus, provenance, and failure story.

HydIR is still early. That is exactly why its language matters. The project can become more capable without becoming less honest—one explicit contract at a time.
