Building HydIR from a 16-byte function

What the native workbench actually recovers, what it emits, and where it refuses to guess.

HydIR is a Rust workbench for inspecting x86-64 ELF files and lifting a deliberately bounded scalar subset to LLVM IR and C. The useful unit of progress is not “a binary decompiled.” It is a chain of separately checkable claims: these bytes belong to a function; these instructions and edges were recovered; this translation preserves the semantics we model; these particular test inputs agreed with native execution.

This note follows the checked-in hydir_max2 fixture. It is small on purpose: the ELF symbol gives HydIR an entry address and a 16-byte extent, while --assume-u64x2 supplies a two-argument SysV AMD64 prototype. The prototype is an analyst assertion, not a fact recovered from the machine code.

Start with bytes, not a picture of a pipeline

The egui workbench below shows the actual disassembly of hydir_max2. The first column is the virtual address; the second is the instruction encoding read from the ELF. The function moves one input into the return register, compares the inputs, and conditionally replaces the result with the other input before returning.

From the five decoded instructions, HydIR recovers five reachable blocks and five direct edges. Recovery is confined to the declared 16-byte extent; an edge into the middle of an instruction or outside that extent is rejected. For a stripped binary, the analyst must provide the entry and size explicitly. HydIR does not infer a trustworthy function boundary from an arbitrary run of bytes.

Lift only the modeled semantics

The accepted instructions become LLVM integer operations and explicit condition checks. The lift uses RDI and RSI as inputs and requires every return path to define RAX. It does not add nsw or nuw promises to wrapping arithmetic. That matters: a pleasant-looking IR file with stronger overflow assumptions would not describe the original program.

In the checked demo script, the relevant commands are:

hydirctl cfg "$demo_dir/max2-original" hydir_max2
hydirctl lift "$demo_dir/max2-original" hydir_max2 \
  --assume-u64x2 --output "$demo_dir/max2-lifted.ll"
opt -passes=verify -disable-output "$demo_dir/max2-lifted.ll"

The exact fixture build, CFG output, IR verification, C emission, and differential checks are in scripts/demo-local.sh. The script also strips the symbol table from a copy and repeats recovery with an explicit entry and extent. The generated IR is an artifact to inspect; passing LLVM’s verifier means it is well-formed IR, not that it is equivalent to every possible execution of the binary.

Compare results on controlled inputs

For trusted fixtures, the demo compiles and runs the original program, the lifted IR, and the emitted C independently. The checked scalar path covers 20 distinct functions, with 1,008 inputs per output path. Those comparisons are useful regression evidence for the supported subset, not a proof of general equivalence. Native validation requires --trusted-fixture because it executes the original binary; it is not a hostile-binary sandbox.

These scripts require Linux x86-64, Clang, and the relevant LLVM tools. On macOS, the repository provides scripts/demo-linux-docker.sh for the containerized demo path.

A refusal is a result

Import, CFG recovery, lifting, C generation, and whole-program rebuild are different contracts. A file can be imported without being liftable. A recovered function can have valid CFG and LLVM IR while C generation fails. The actual workbench diagnostic below is one such case: an unsupported Call stops C output, while the UI keeps the earlier artifacts available.

The current function lift rejects memory access, calls, indirect control flow, partial-register operations, unknown instruction semantics, and uninitialized reads. Whole-executable rebuild has a separate, stricter contract for trusted static freestanding programs. None of this is a general decompiler, and opening a local ELF in the desktop app does not upload it.

What would make the next increment credible?

Broader instruction and memory support should arrive with a fixture that demonstrates the new semantics, a negative case that must still refuse, independently verified output, and a differential report with the precise inputs tested. That is the development loop HydIR can scale without blurring “we parsed it,” “we translated it,” and “we checked it.”
