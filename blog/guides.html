Desktop workbench

Open a local little-endian x86-64 ELF in the hydir app. The overview shows the program inventory and analysis status. Select a function to connect its machine address and bytes to disassembly, control flow, P-code effects, and generated views. The Ghidra worker starts automatically for local ELF analysis and its project is cached for later selections.

  1. Pick a function. The checked-in demo/hydir-prism.elf includes named entry points. hydir_stage_decision shows branching control flow; hydir_stage_call_chain shows a direct call.
  2. Inspect the evidence. Read the instruction and CFG views before interpreting a generated representation. A recovered function boundary or edge carries evidence and may still have unresolved targets.
  3. Compare outputs. Open the available IR and C views and read diagnostics alongside them. A C rendering can preserve unknown effects explicitly without proving that it can be safely rewritten.

The Ghidra P-code article explains the imported operations behind one x86 instruction. For the native pipeline's control flow and SSA, see From Graphs to Code.

Observe a selected function with Frida

In the desktop app, open an ELF and select a function, then choose the top-level Frida observation tab. Its Observe with Frida panel opens automatically. Enter an InputSpec JSON path and choose Observe selected function. The same panel is available in Ghidra P-code. This runs that ELF with the specified input and records observed blocks and calls for the selected function. The panel can copy the observation JSON, use captured entry registers as a P-code seed, and plan observed indirect calls.

Availability: the observation action requires Linux x86-64, a local ELF, a Ghidra snapshot with a mapped selected function, a nonempty InputSpec path, and the optional Linux Frida observer bundle. It is disabled when those conditions are not met. Ordinary Windows builds can still inspect the ELF and its static analysis.

Frida evidence is tied to that binary and input. Observed blocks and calls are byte checked; unobserved paths remain unknown. A completed trace does not prove the process exit code or whole-program equivalence.

Command line

hydirctl makes the same analysis useful in scripts. Start with doctor to check the local toolchain, use discover to enumerate function candidates, and request a specific stage with lift or a C view with decompile. Ghidra commands can save a binary-bound snapshot for later verification and coverage inspection.

cargo run --locked --bin hydirctl -- doctor
cargo run --locked --bin hydirctl -- discover demo/hydir-prism.elf
cargo run --locked --bin hydirctl -- lift demo/hydir-prism.elf --function hydir_stage_decision --ir state
cargo run --locked --bin hydirctl -- decompile demo/hydir-prism.elf --function hydir_stage_decision --view unit

The native decompiler reference lists stage contracts, limits, supported instruction families, and reproduction commands. The Python SDK reference covers local Ghidra operations and authenticated service workflows.

Read the result

Look for separate structural, semantic, verification, and rewrite-readiness claims. partial control-flow recovery means some edges remain unresolved. unknown or conservative semantics mean the representation retains uncertainty. not_run verification means no execution comparison has been made. Exactness is relative to the recorded machine and environment model.

When a stage stops: keep the diagnostic and the source location with the artifact. An explicit refusal or opaque effect identifies the unmodeled boundary; it does not invalidate earlier, independently recovered facts.

For the distinction between native C generation and the restricted scalar LLVM path, read the architecture guide. The compiler-theory article explains why control-flow joins, memory effects, and SSA matter to both paths.
